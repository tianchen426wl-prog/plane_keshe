# 数据库自动初始化与成员启动

实施日期：2026-11-20。数据库结构版本保持 V8，新增 Flyway 8.5.13 管理及自动建库，不重置已有业务数据。

## 1. 成员首次运行

成员先安装并启动 MySQL，配置自己的数据库账号、密码与 JWT 密钥，再构建并启动后端。**不需要先创建 air_ticket，也不需要手动导入任何 SQL。**

推荐沿用根 README 的环境配置流程：

```powershell
# 项目根目录，PowerShell 7
./scripts/setup-env.ps1
# 编辑生成的 .env，填写本机 DB_USERNAME / DB_PASSWORD、JDK/Maven 路径
notepad .env
. ./scripts/activate.ps1
mvn.cmd -f air-ticket-server/pom.xml -DskipTests package
./start_backend.ps1
```

已有 `.env` 或 `.local/application-local.yml` 的成员保留自己的设置，不覆盖配置，不接收其他人的真实密码和模型密钥。也可按 README 使用 `scripts/run-server.ps1 -Port 18080 -Database air_ticket`；它与直接 Java/IDE 启动使用相同的数据库初始化代码。直接 Java/IDE 启动时须自行传入环境变量或提供可读取的本地 YAML，PowerShell 的 dotenv 加载不属于 JVM 的自动行为。

程序启动顺序：

```text
读取连接配置
  → 连接配置指定的 MySQL 数据库
  → 仅遇到“数据库不存在”时连接服务器并创建该库
  → 获取按库隔离的初始化锁
  → 空库执行 V1～V8 / 已有项目库受控接管
  → 校验并执行待应用的 Flyway 迁移
  → 启动 HTTP 与业务组件
  → 补齐未来日期的航班和座位
```

首次需要 CREATE DATABASE、建表/改表、创建视图/存储过程/触发器等权限。若 MySQL 尚未安装、未启动、密码错误或权限不足，程序会明确失败；自动建库不代表自动安装 MySQL 服务。账号对已有完整库不需要额外 CREATE DATABASE 权限。

默认 `DB_INITIALIZE=true`、`DB_CREATE_IF_MISSING=true`。前者关闭时由维护者自行准备完整结构；后者关闭时仅禁止创建缺失库，已有库仍会执行迁移。初始化失败会阻止业务服务启动，不忽略错误继续运行。

## 2. SQL 文件已归一

唯一正式目录：`air-ticket-server/src/main/resources/db/migration/`。

| 版本 | 用途 |
|---|---|
| V1__baseline.sql | 基础表、默认管理员、菜单、索引、视图、过程与审计对象；不导入历史用户或过期航班 |
| V2__booking_security.sql | 用户/管理权限、占位锁价、订单快照与库存兼容 |
| V3__integrity.sql | 数据完整性约束 |
| V4__inventory_views_and_history.sql | 库存健康视图及业务历史删除保护 |
| V5__schedule_fares_seats_ai.sql | 机场、布局、班期、费用、座位及 AI 结构 |
| V6__official_airlines_demo_catalog.sql | 14 家航司、25 个机场、演示布局/费率与 112 个班期 |
| V7__asset_metadata_and_health.sql | 本地素材字段和座位健康视图 |
| V8__refund_procedure_seat_safety.sql | SQL 退款过程与费用、座位的一致性 |

这 8 份 SQL 和 Flyway MySQL 模块随 Maven 打入可执行 jar，运行时不依赖源码目录或 mysql.exe。旧 SQL 已移到 `air-ticket-server/sql/legacy/`，不会被扫描，保留用于追溯，不能导入正在使用的库。`sql/README.md` 说明了目录分工。

V1 不包含旧全量脚本的清表、历史乘机人和固定日期航班导入。首次运行创建的管理员为 `admin / admin123`，普通旅客自行注册；业务航班由班期系统按当前日期生成。

`scripts/build_flight_catalog.py` 只将候选 SQL 写到本地忽略目录 `.local/generated`，不再覆盖已发布的 V6。后续变更添加新的 V9 等迁移，不能修改已经执行的文件，否则 Flyway 校验会停止启动。

## 3. 已有库和异常处理

- 缺失库：只创建连接配置中指定的库，不修改其他库。
- 已有空库：正常执行 V1～V8。
- 已有 V1～V8 项目库：先检查基础表和旧版本记录；通过后按实际旧版本记入 BASELINE，再执行更高版本。
- 已有 V8 库：只建立 Flyway 管理记录，不重导 V1，不重置管理员、订单、舱位库存或航司资料。
- 已由 Flyway 管理：验证校验和，执行新增版本；重复启动不重新灌入数据。
- 非项目非空库、结构不完整、旧版本不连续、脚本被修改：停止并保留现场，不猜测版本，不自动 clean/repair。

`flyway_schema_history` 是新迁移权威记录；`schema_version` 保留供旧库兼容。新空库会有 V1～V8 SQL 记录，原 V8 库可以只有一条 V8 BASELINE，两者都正常。

并发初始化通过同一连接持有/释放 MySQL 命名锁，覆盖创建 Flyway 历史表之前的接管阶段；Flyway 自身继续负责迁移锁和版本校验。MySQL DDL 不能整体回滚，失败迁移应由维护者核对实际状态并处理，程序不会清表重来。

迁移前建议备份。现有 `scripts/backup-db.ps1` 仍使用 mysqldump，默认本机连接；非本机环境请使用对应备份工具。

## 4. 可选维护入口

正常运行项目直接启动后端。需要只执行数据库维护时：

```powershell
# 先构建 jar，再在根目录运行
./scripts/install-db.ps1 -Database air_ticket    # 缺失/空库；非空会拒绝
./scripts/upgrade-db.ps1 -Database air_ticket    # 已有库；缺失会拒绝
```

两者均转入 `scripts/database-setup.ps1`，调用 jar 的 `--database-init-only=true` 模式，使用相同的连接配置和 Flyway 迁移。执行完退出，不启动 HTTP、占位清理或航班生成；正常后端启动后再生成日期航班。

数据库账号/地址通过项目环境配置读取；正常安装/升级不再依赖 mysql.exe。旧 -DemoData 不再导入固定日期样例；依赖私有备份的 -RestoreTest 已退役。

### 只有 jar 的实际首次运行

`scripts/smoke-database-bootstrap.ps1` 将 jar 复制到隔离目录，不提供源码 SQL 文件，子进程 PATH 不含 mysql.exe；数据库事先不存在。验收通过：

- 后端自动建库并执行 8 个迁移。
- 导入 14 家航司、112 个班期；测试配置 2 天窗口生成 224 个航班。
- 新管理员可登录，用户注册、查询、报价、选座占位和模拟支付成功。
- 重启同一 jar 后已支付订单保留，新增日期航班为 0。
- 客舱库存、座位库存与容量差异均为 0。

该测试的 2 天窗口仅为了缩短隔离验收；正常项目仍为 30 天。测试结束停止自有进程并删除自有临时库，不影响正式库。证据：[jar 启动验收](evidence/database-bootstrap-jar-smoke.json)。
