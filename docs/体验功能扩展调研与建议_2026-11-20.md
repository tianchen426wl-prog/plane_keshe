# 航空售票系统体验功能扩展调研与建议

调研日期：2026-11-20。范围：当前门户、管理后台、后端业务服务、数据库迁移与项目文档，以及公开官方产品与开发资料。本报告提供功能分析和实施建议，不改变业务代码、数据库或运行配置。

## 1. 结论

项目已经有较完整的单程购票基础。下一阶段最有价值的投入，是让用户更容易选到合适的航班、减少重复填写，并在买票后继续获得行程和异常处理服务。

建议第一批做：**搜索人数与筛选、AI 推荐到预订的衔接、常用乘机人、完整订单详情与行程卡片**。第二批建设站内消息、航班动态和取消处理，再推进往返、改签和候补。

这些建议根据源码中的现有能力与扩展成本排序，不是用户访谈或线上转化数据的结论。后续可通过任务完成率、重复填写次数、查询无结果后的继续操作比例验证价值。

## 2. 已有能力：应继续利用

| 业务环节 | 当前代码或资料体现的能力 | 下一步性质 |
|---|---|---|
| 航班目录 | README 记录 14 家航司、25 个机场、112 个每日班期；后端按班期补齐未来日期 | 扩展场景，不必只追求增加航班数量 |
| 低价日期 | 已有逐日最低含必付费用价格、前后一天、售卖窗口限制 | 优化呈现与筛选一致性 |
| 搜索 | 城市/机场、日期、航司、起飞时间/价格排序 | 增加人数、预算、时段、舱位等条件 |
| 预订 | 经济/商务舱、1～5 位成人、具体座位、免费自动分配、费用明细、报价与限时占位 | 衔接和操作体验升级 |
| 订单 | 模拟支付、订单列表、费用与座位详情、退订试算、管理员审核 | 补足完整行程、进度与售后 |
| AI | DeepSeek 解析国内成人直飞单程需求，查询本地库存，生成候选，保存方案 | 完善偏好、历史入口、预订衔接 |
| 后台 | 菜单权限、航班与班期管理、生成记录、退款处理、订单审计基础 | 增加主动服务与经营分析 |

这里的航班、票价、座位布局和支付均沿用项目的课程演示定位。公开官网的真实业务能力用于产品参考，不代表本项目具备真实出票能力。

## 3. 从源码确认的关键体验缺口

### 3.1 查询人数与购票人数分离

`SearchPanel.vue` 没有人数输入；`FlightSearch.vue` 的 `fetchPage` 没有传 `quantity`，后端接口默认人数为 1。人数在选舱弹窗中才调整。

因此，用户为多人买票时，搜索结果可能包含只够 1 人、却不够整组同行人预订的舱位。建议将人数前置到搜索阶段，并贯穿搜索结果、日期价格、AI、报价和预订。

### 3.2 AI 推荐没有完整传到预订

`AiPlanner.vue` 的 `choose` 方法只传出发城市、到达城市和日期，没有携带候选 `hbid` 或人数。用户点击具体候选后仍要重新找到航班、选择人数。结束核查时已重新读取该页面的最新版本；页面已提供自然语言与表单两种需求输入，但上述跳转衔接仍未补齐。

服务端解析约束主要为城市、日期、人数和预算；排序请求也只包含这些约束和候选。诸如“不坐早班”“晚上到达”的原始偏好，没有结构化传递到排序阶段。现阶段不能把这些偏好描述成已可靠支持。

### 3.3 旅客资料无法直接复用

个人中心有账户资料与密码设置，购票弹窗要求逐个填写姓名。数据库已有订单乘机人记录，但它不是可独立维护的常用乘机人档案。

### 3.4 购票后缺少集中行程服务

门户订单主要展示状态、路线、起飞时间、数量、费用和退订入口。可以进一步整合航班号、抵达时间、航站楼、行李规则、行前提醒和退款进度，形成独立详情页。

已有 `flight_snapshot`、`price_snapshot`、订单日志等基础，不建议重新造一套订单。应区分“购票时约定”与“当前航班动态”，两者分别展示。

### 3.5 航班异常有计算基础，缺少完整操作流程

当前有 `operational_status` 字段、取消状态展示及取消航班全额退款计算。但从现有控制器、管理页面与状态写入检索，未看到完整的航班取消/延误发布、旅客通知、替代方案与处理进度流程。

停售、取消和延误应分别定义；不能把“停售”当作取消，也不能只改一个状态就认为受影响旅客已经得到处理。

## 4. 功能候选与优先级

P0 是优先提升现有流程；P1 是扩展核心出行场景；P2 是进一步丰富体验。成本为相对判断：小主要是页面与现有接口衔接，中需要新接口/数据结构，大涉及多订单或库存状态变更；不是排期承诺。

| 优先级 | 功能 | 用户能感受到的变化 | 相对成本 |
|---|---|---|---|
| P0 | 搜索人数与丰富筛选 | 多人同行可一次找到够票、预算和时段合适的航班 | 中 |
| P0 | AI 推荐直接衔接预订 | 点选推荐后保留航班、人数和条件 | 小～中 |
| P0 | 常用乘机人 | 为自己或同行人再次购票时直接选择 | 中 |
| P0 | 订单详情与行程卡片 | 买完票后有清晰、可保存的行程信息 | 中 |
| P0 | 移动端购票步骤优化 | 选舱、填人、选座、确认费用更易操作 | 中 |
| P1 | 站内消息与进度提醒 | 能看到支付、退款、航班变化的处理结果 | 中 |
| P1 | 航班动态与取消处理 | 航班变化后有说明、通知和可执行的处理入口 | 大 |
| P1 | 收藏、最近搜索、低价/余票提醒 | 对尚未决定的出行方案持续关注 | 中 |
| P1 | 成人往返预订 | 去回程集中查询和管理 | 大 |
| P1 | 改签 | 改变出行计划时查看差价和规则后办理 | 大 |
| P1 | 售罄候补 | 没票时登记，释放余票后按规则获得机会 | 大 |
| P2 | 航班对比与目的地探索 | 比较 2～3 个方案，或按预算找目的地 | 中 |
| P2 | 座位偏好与同行连座 | 靠窗/靠过道/免费优先，并明确能否坐在一起 | 中 |
| P2 | 模拟值机与演示登机牌 | 从购票延伸到出发前的完整体验 | 中～大 |
| P2 | 行李与餐食等附加产品 | 在报价中选择实际需要的服务 | 中～大 |
| P2 | 后台趋势与业务分析 | 管理员能了解销量、退款和占位转化 | 中 |

## 5. 优先功能如何落地

### A. 搜索人数、筛选与航班对比

- 前置成人数量；增加起飞/到达时段、总预算、舱位、指定机场、行李额度和仅看可售航班。
- 筛选改变后回到第一页；清晰显示已选条件和清空入口，保留路由中的查询条件。
- 日期条应与人数及适用筛选保持一致；若按“单人最低价”展示，必须明确标注，不能暗示多人一定有票。
- 筛选、计数和排序放到后端。只筛当前 20 条分页结果，会让总数与排序产生误导。
- 后续支持 2～3 个航班横向对比：出发/抵达时间、总费用、行李、退订条件。项目已有含必付费用展示，应在此基础上扩展。

验收：选择 3 人后，可订结果必须有满足 3 人的同一可售舱位；预算按明确的单人或整单口径计算；翻页后条件不丢失；无结果时能一键调整日期或清除条件。

### B. AI 推荐衔接与偏好支持

- 点击候选后携带航班 ID、人数、日期和已解析条件；在搜索页定位并打开目标航班。
- 所有库存和价格继续由正常报价接口重验，AI 推荐不直接生成已支付订单。
- 将“不早起”“晚间抵达”“行李不少于 20kg”等转成可验证条件；硬条件由后端过滤，软偏好用于排序，并显示推荐原因。
- 服务端已有方案保存与按用户读取能力，可增加“我的规划”和重新查询入口，而非重复建设存储。
- 规划失败时保留已输入文本和已解析条件，方便切换普通搜索。

验收：AI 推荐 2 人某航班，进入预订仍是该航班与 2 人；航班停售后明确说明并给替代候选；超预算不应由模型忽略；没有匹配结果时解释可调整的具体条件。

### C. 常用乘机人与填写恢复

- 新增常用乘机人管理与默认本人；支持添加、编辑、删除、批量勾选同行人。
- 首版仍按成人演示范围实现，不强行扩展儿童/婴儿定价。
- 按实际展示需要设计字段；如加入证件，应使用演示资料、默认脱敏，并在服务端按账户校验所有权。
- 常用档案修改不应回写历史订单；下单时保存当次乘机人快照。
- 返回上一步或报价失败时保留非敏感输入；退出账户清除临时旅客数据。

验收：两名同行人可一次勾选；甲账户不能读取或选择乙账户档案；修改常用姓名不会改变既有订单；失败重试无需从头输入。

### D. 完整订单详情与行程卡片

- 将费用弹窗扩展为详情页：航班号、机场/航站楼、出发/抵达、乘机人和座位、行李、订单费用、退款规则。
- 展示时间线：创建占位、模拟支付成功、申请退订、审核通过/拒绝及理由。审计日志转为用户能理解的业务事件，不直接暴露内部日志。
- 增加“即将出行”“已结束”等行程视图；行程阶段与订单付款/退款状态分开维护或推导。
- 提供打印版行程卡与 ICS 日历文件。课程演示行程卡明确标识演示用途，避免被理解为真实客票或报销凭证。

验收：一次模拟购票后能在独立页面查全关键信息；退款拒绝能看到原因；日历导入时间与页面北京时间一致；当前航班变化不会覆盖购票时费用规则。

### E. 移动端与可访问性

现有页面已有媒体查询、骨架屏、错误提示，座位按钮也有部分可访问性属性，建议持续完善。

- 将较长选舱弹窗拆成明确步骤，移动端使用全屏抽屉或独立页面；固定底部费用合计与下一步。
- 座位除了颜色，还显示文字/图标区分已选与不可用，保留键盘焦点，明确靠窗/过道与额外收费。
- 关键错误贴近对应字段，汇总提示与重试入口配合使用；价格和库存刷新避免突然跳动。
- 倒计时以服务器时间校准，但不每秒向读屏工具播报；在即将到期和已到期时提示。

验收：在 375px 宽度下可以完成选舱、多人填写、选座和确认；键盘可完成关键操作；异常后用户清楚哪些信息已保存、哪些操作需要重试。

## 6. 第二批：让购票后的服务连贯起来

### F. 站内消息与航班异常

先做站内消息：支付结果、退订审核结果、临近出发和航班变更。支持未读数、按订单跳转、重复事件去重。邮件/短信可后续接入，不是首版依赖。

后台增加受控的航班变更操作，记录原状态、新状态、原因、计划/预计时间、操作者和时间。发布前展示受影响订单数；发布后同步停售/占位处理和站内通知。

取消流程应复用已有全额退款计算，补齐申请或审核策略；不默认批量退款。延误后的退款资格应使用明确的演示规则，不能简单复用“取消”判定。

验收：取消已售航班后无法新增购买，待支付占位有明确处理，已购旅客收到一次通知并能进入处理页面；相同操作重试不重复释放库存或产生退款。

### G. 收藏、低价与余票提醒

最近搜索和收藏可以先做轻量版本，登录后保存到账号；订阅条件包括路线、日期范围、人数、舱位和预算。初版以站内提醒为主。

当前班期生成按模板基础价设置舱位价格，未见完整市场价格历史采集机制，因此不要直接提供“历史最低价”“未来会降价”等结论。可以先基于本地实际报价快照记录变化，并在管理端提供可解释的演示调价场景。

低价提醒需要明确总价口径与采集时间；无可售结果不能记为 0 元；触发后再次检查库存，并做去重和频率控制。余票提醒只告诉用户可以重新查看，不代表已锁住座位。

### H. 往返、改签、候补

**往返：**首版限定国内成人直飞，集中展示去程与返程。先建立行程主单与分航段订单关系，明确两段是否共同占位、支付和取消。一次确认两段时，任一段失败不能留下未说明的半张行程；若允许分开购买，必须分别展示成功结果。

**改签：**先给可改航班、差价、改签费和新规则，再确认。先锁新库存，成功后释放原库存；失败保留原票；重复提交不能重复扣费或重复回补。应在订单详情、消息和异常处理稳定后开展。

**候补：**现有限时占位不是售罄候补。首版可选择成本较小的“余票提醒”；若实现候补分配，则建立排队、获配待支付、超时、取消、完成状态，先定义同等条件按提交顺序、人数是否整组满足、价格上限及有效期。获配必须调用已有库存与占位流程，不能后台直接把订单改为成功。

## 7. 进一步丰富体验的功能

- **目的地探索：**“从北京出发、未来周末、总预算 1000 元以内去哪儿”，结合现有机场和航班目录生成目的地卡片。首版仅覆盖本地可售库存；地图为后续可选展示。
- **连座与座位偏好：**已有自动分配优先同排，可增加免费优先、靠窗/过道和“必须连座/允许分散”。连座失败需用户选择，不悄悄加价或拆散同行人。
- **模拟值机：**为已购订单增加值机窗口、确认旅客和座位、演示登机牌。先定义退款/改签后的失效规则，演示二维码仅用作项目内查询。
- **附加服务：**额外行李、餐食需求和特殊协助。产品支持范围、价格、服务库存、退款方式都需明确，并纳入报价和订单快照，不默认勾选收费项目。
- **帮助与反馈：**增加与订单关联的反馈/工单、常见问题和服务进度，比单纯新增无上下文的聊天框更实用。
- **后台分析：**从目前四项计数扩展到每日订单金额、退款金额、净额、占位支付转化率和热门航线。区分下单日与出发日、区分待支付与已支付，记录异常退款和生成失败等待办。

## 8. 建议实施顺序与数据落点

| 批次 | 交付范围 | 可考虑的数据/API 扩展 | 完成标志 |
|---|---|---|---|
| 第一批 | 人数与搜索、AI 衔接、常用乘机人、订单详情、移动端操作 | 扩展现有 flights 查询；增加 passenger_profile；复用 ai_plan、订单快照与业务事件 | 从需求到预订无需重复选择，买后能查完整行程 |
| 第二批 | 消息、退款进度、航班动态与取消服务 | user_notification、flight_change_event、消息去重与待投递记录 | 航班发生变化后，相关订单、占位和旅客能得到一致处理 |
| 第三批 | 收藏、报价历史、价格/余票订阅 | saved_search、flight_subscription、fare_observation | 提醒能准确触发、可取消、不重复，价格来源可解释 |
| 第四批 | 成人往返，再视需要做改签和候补 | itinerary 与分段订单关系；change_request；waitlist_entry | 多航段或换票失败不会破坏原订单与库存 |
| 第五批 | 模拟值机、目的地探索、附加服务和后台分析 | 按所选功能增量设计 | 能演示完整出行故事，已有购票退款流程保持可用 |

新增表名仅为建议，不是已经存在的表。迁移应延续当前 Flyway 版本体系，不能回改已执行的 V1～V8 脚本。

不建议为了这些功能先引入微服务、消息队列或 Redis 集群。当前课程规模可从 Spring 事务、MySQL 状态表、定时任务和轻量消息轮询开始，是否更换架构由实际瓶颈决定。

## 9. 可用于答辩的完整演示

1. 输入“两位成人、北京到上海、不坐早班、总预算 2500 元”。
2. 查看满足条件的候选，比较行李、到达时间和费用，点击后保留目标航班与人数。
3. 勾选两名常用乘机人，申请免费连座，确认费用并模拟支付。
4. 在“我的行程”查看完整行程卡、座位、规则，导出日历。
5. 管理员发布演示航班取消，旅客收到站内消息，查看退款试算并申请处理。
6. 管理员审核后，旅客看到完整进度，后台可核对金额、库存和操作记录。

这组演示需要上述新增功能完成后才能成立，不代表当前项目已全部支持。
