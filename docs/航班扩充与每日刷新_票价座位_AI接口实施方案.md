# 航班扩充、每日刷新、票价座位与 AI 接口实施方案

项目：plane_keshe。调研日期：2026-11-20。

本文根据本轮四项需求制定实施方案，结合现有 Spring Boot、MyBatis、MySQL、Vue 2 / Element UI 项目。本文新增的是方案文档，尚未下载新素材、变更业务代码或执行数据库迁移。“作为选择”按“座位选择”理解。

## 1. 推荐实施范围

建议完成一套“官方航司资料 + 本地图片 + 按日期生成的演示航班 + 费用明细 + 具体座位 + AI 查询接口”的课程系统。

| 需求 | 首期交付 | 数据性质与边界 |
|---|---|---|
| 航司和航班扩充 | 现有 8 家扩为 14 家；约 20 个城市、25～30 个机场；40～60 条有向航线 | 航司介绍来自官网；航线、时刻、价格和库存为明确标识的课程演示数据 |
| 每日刷新 | 默认可查今天起 30 天；每天补齐最远一天，启动时自动补漏 | 30 天是项目配置，不是航空业统一规定 |
| 航班详情和费用 | 机场、航站楼、抵达时间、机型、行李、退改说明；服务端报价与锁价 | 不把模拟金额称为航司实时官方价格 |
| 座位选择 | 按客舱布局选座，支持自动分配，联动占位、订单、退订 | 未核实的布局标注演示布局，不冒充特定航司真实配置 |
| 大模型接口 | 提供商适配层、受控航班查询工具、结构化规划协议，默认关闭调用 | 本轮目标是预留接口；没有模型配置时正常购票仍可使用 |

建议生成每天约 100～200 个航班实例，30 天约 3,000～6,000 条，具体数量由班期计算。数量是容量目标，不是调研得到的真实航班统计。首期覆盖国内成人、人民币、直飞和独立往返；儿童、婴儿、国际、多币种、真实出票另行扩展，不能用固定成人折扣模拟其完整规则。

真实航班接入另设 `FlightDataProvider`。演示提供商与外部提供商使用不同数据源标识。未来接入合法 API 时再核对覆盖范围、访问资质、测试/生产环境、费用和出票能力，不抓取官网购票页面来冒充实时库存。[Duffel 官方入门文档](https://duffel.com/docs/guides/getting-started-with-flights)展示了搜索报价到预订的 API 流程，可作适配层参考，当前不绑定供应商。

## 2. 现有代码核对与必须解决的问题

| 当前情况 | 本次处理 |
|---|---|
| `Hbxx` 主要是出发时间、城市文字、时长文字、价格 | 增加机场实体、计划到达时间、服务日期、机型布局、数据来源；保留旧字段兼容读取 |

| 当前退款有统一时间限制 | 新票使用版本化票价规则；旧订单保留原有语义，不追溯套用新规则 |
| 图片工具按中文名称映射 8 家公司，含外部占位图与模糊匹配 | 改为稳定航司 ID/代码与数据库图片路径，使用本地占位图，避免航司错配 |
| 选舱已存在，具体座位尚未建模 | 分清客舱等级、销售产品和座位号；不要把选择经济舱当作选择 12A |

迁移不能更换已有航班和订单的主键，不能清空重建业务表。旧订单的金额、行程快照与退款记录必须可追溯。

### 3.2 图片下载与引用方案

实施阶段逐家整理品牌 logo 与封面图，至少一张有效本地封面；logo 只有在来源与使用条件明确时引入，缺失时显示文字品牌。现有图片也一并追溯来源，无法核实的替换。

建议目录：

```text
air-ticket-web/portal/public/images/airlines/{stable-airline-key}/logo.png
air-ticket-web/portal/public/images/airlines/{stable-airline-key}/cover.webp
air-ticket-web/portal/public/images/airlines/placeholder.svg
docs/assets/airline-assets.json
```

`stable-airline-key` 优先使用核实后的航司代码，否则使用内部稳定编号。数据库分别存 `logo_path`、`cover_path`，不再用中文名称猜测文件。后台若需要同样素材，构建时复制同一份清单指定资源到 admin 的公开目录，或由后端提供统一静态资源地址，不能假设 portal 的 public 目录能被 admin 直接访问。

素材清单包括：航司 ID、资源类型、来源页面、原图 URL、下载日期、作者、授权/使用条件、署名要求、本地路径、SHA-256、格式、尺寸、审核状态。官网可访问不代表图片可以自由转载；公开分享课程仓库前按素材的实际许可处理。照片可选逐文件核实许可的开放图库，保留作者和来源，不使用搜索缩略图代替原图。

下载工具限制来源域名与重定向目标，校验文件大小、真实 MIME 和解码结果；拒绝 HTML 伪图片；SVG 仅接受审核后的安全版本，否则转换为位图。封面输出合理尺寸的 WebP/JPEG，logo 保留透明度与品牌比例。页面提供 alt、懒加载和本地错误兜底，不依赖外网热链。下载失败明确记录，不能把占位图计为该航司素材已完成。

## 4. 每日航班刷新与按日期查询

### 4.1 数据模型：班期与每日实例分离

新增 `flight_schedule` 保存重复执行规则：航司、航班号、出发/到达机场、有效起止日期、星期掩码、当地起飞/到达时间、到达日偏移、机型布局版本、默认销售产品、模板版本、启停状态。

`hbxx` 继续作为具体日期的航班实例，增加：

- `schedule_id`、`schedule_version`、`service_date`：出发机场当地服务日期；旧航班可不关联模板。
- `departure_airport_id`、`arrival_airport_id`、计划起降时刻、机场时区、航站楼和整型分钟时长。
- `aircraft_layout_version_id`、`source_type`、外部来源标识、最后同步时间。
- `sale_open_at`、`sale_close_at`、销售状态、运行状态。运行取消与售罄、停售分开表示。

日期实例唯一键优先 `(schedule_id, service_date)`；另为手工/导入记录设置航司、航班号、服务日期、出发机场、到达机场的业务唯一键。同一班号多航段可存在，代码共享首期不启用。删除旧 `uk_flight_no` 前先审计重复及空值；不能只删索引而没有新的约束。

机场表保存城市、机场名称、代码、IANA 时区。数据库保存规范化时刻，接口显式返回偏移/时区；展示起降机场当地时间及“次日 +1”。查询服务日期用起飞机场当地日界线换算为时间范围，避免对时间列套日期函数导致索引失效。

### 4.2 调度策略

采用现有 Spring 调度能力，每天 **00:05，Asia/Shanghai** 触发，默认确保 `[今天, 今天+29天]` 的应生成实例完整。窗口与调度时间可配置。应用启动后执行同样的补齐流程；停机三天后重启应补齐遗漏，不依赖每天始终在线。

处理步骤：

1. 获取任务互斥锁，记录本次运行 ID、日期范围及模板版本。
2. 按模板有效期、星期和停飞例外计算应生成日期，不是所有航班每天都飞。
3. 对缺失实例生成航班、布局关联、舱位库存和销售产品，一条实例的相关数据原子提交。
4. 已存在实例跳过；发现版本不同只产生差异待办，不覆盖已有占位、座位、价格和订单。
5. 记录新增数、跳过数、失败数和各日期覆盖情况，失败任务可重试。
6. 更新查询缓存与后台任务状态；普通交易仍实时校验数据库库存。

**刷新绝不清零订单、重置余票、重建主键或把昨天的航班改成今天。** 过期航班停止售卖并保留历史。模板停售不隐式取消已售航班；已有航班取消必须走单独的运行变更和非自愿退款处理。

初期单 MySQL 环境采用数据库命名锁防止多应用同时补齐，持有专用连接并在 finally 释放；连接丢失立即终止该轮，不在失锁后继续写入。唯一键和短事务仍是最终幂等保障。MySQL 命名锁与连接关联、不会随事务提交自动释放，不能在普通连接池随机取连接加锁/解锁。[MySQL 官方说明](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html)。定时配置参考项目对应的 [Spring 5.3 调度文档](https://docs.spring.io/spring-framework/docs/5.3.31/reference/html/integration.html#scheduling-annotation-support-scheduled)。

`flight_generation_run` 记录窗口、心跳、错误摘要和结果；后台提供“补齐缺失航班”与任务记录查看权限，不提供一键重置全部库存。按日期批处理，避免一个事务锁住整个 30 天窗口。

### 4.3 售卖窗口与前端查询

借鉴 12306 的日期导航、条件查询、余票和开售提示。12306 官方目前说明铁路互联网预售为 15 天含当日，并可临时调整；这不代表航空应采用同样规则。[12306 官方说明](https://help.12306.cn/cms/answer/h5/001531826595438842083440b580b2e0)

- 日期条支持前后日期和日历，服务端返回窗口起止、服务器时间、数据状态；超范围日期不能伪装成“无航班”。
- 明确区分未开售、可售、售罄、停售、取消、当天无班期、数据尚未生成、查询失败。
- 生成时间与开售时间分离：可以先生成明天实例，到达配置的开售时间才允许占位。
- 增加机场/城市、航司、时段、客舱、含税预算、是否有托运行李筛选，按含必付费用的最低可售总价或起飞时间排序。
- “低至”价格必须存在可购买产品，且人数条件满足；不能用无库存价格或 `hbxx.price` 旧缓存排序。
- 余票变化可在页面可见时按配置短轮询，例如 60 秒；暂停后台标签页轮询，切日取消旧请求，提交前强校验。每日生成与页面余票刷新是两件事。
- 首期不复制铁路候补机制；售罄明确提示，不虚构排队成功。

## 5. 航班详情、费用与规则

### 5.1 用户应看到的详情

航司标识、航班号、出发/到达机场与航站楼、完整起降日期时间、跨日、飞行时长、机型、客舱、行李额度、餐食/服务说明、退改条件、费用明细、可售数量、数据来源和更新时间。未接入运行数据时，登机口、延误状态和准点率显示未知或不展示，不编造信息。

### 5.2 分清三个概念

| 概念 | 示例 | 对库存的影响 |
|---|---|---|
| 物理客舱 | 经济舱、商务舱 | 布局确定该舱物理座位数 |
| 销售产品 | 经济基础、经济灵活 | 引用同一客舱库存，具有不同价格、行李及退改条件 |
| 具体座位 | 12A、12B | 一张票对应一个具体座位；不是新的票额来源 |

首期同舱多个产品共享 `hbxx_cabin` 库存，不给每个产品复制整舱票额。若后续引入独立折扣配额，必须同时满足产品配额和物理客舱总量限制。机型只有经济舱时不能强行生成商务舱和头等舱；停止按固定 60%/30% 比例构造所有飞机的三舱。

### 5.3 计价与锁价

费用按旅客、航段和可选服务分别列项：

```text
旅客航段金额 = 基础运价 + 适用税费 + 适用附加费
订单应付 = Σ旅客航段金额 + Σ经用户选择的附加服务金额 - 有效优惠
```

附加服务可含付费选座、额外行李；已包含的服务不能重复收费。首期优惠可保持为 0，先完成正确报价。税费与附加费采用带来源、适用人群、适用日期及版本的配置，不能把当前某个航司的金额写死为所有航班永久规则。区分按出票日期与按出行日期生效的政策。

南航运输条件将票价、税费等作出区分，特价产品另有使用条件；因此本项目应采用产品规则与费用组成建模，而非一个通用价格乘数。[南航官方运输条件](https://www.csair.com/newh5/cn/tourguide/booking/orders/order/gnysztj/)

演示计价可采用“路线基准价 + 有效期定价表 + 产品差异价 + 已选择服务”，所有配置标注演示。首期不采用每次查询随机涨价；不声称算法能推算真实市场机票价格。节假日和库存阶梯如需启用，采用可审计的策略版本并保护既有锁价。

报价流程：

1. 服务端根据航班、产品、旅客数、座位/服务选择生成 `quoteId`、费用明细、规则版本和 `validUntil`。
2. 占位时验证报价未过期、归属、库存、产品版本及服务资格，并在同一事务锁定票额和座位，保存费用快照。
3. 占位成功后在其有效期内按快照确认；已锁定报价不能因管理员调价而静默变化。可选服务变化必须重新报价并由用户确认。
4. 过期后重新报价；不能沿用前端旧总额。过期截止时间由服务端决定，并与外部报价有效期取更早值。

金额使用 `BigDecimal` / `DECIMAL`，定义按项舍入到分的规则；返回币种。订单持久化 `base_fare`、各项费用、服务费、总价与规则版本。新增 `quote`、`quote_item` 和 `order_price_item`，占位也保存同样的不可变金额快照。旧 `unit_price` 字段维持兼容用途，新交易不再仅靠它重建完整价格。

例：基础运价 600、税费 50、附加费 40、选座 20，单人总额为 710，两人为 1,420。这组数值仅用于说明求和，**不代表现行收费标准**。

### 5.4 退改与取消

保存产品规则版本、起飞前各时间段费用、禁止/允许条件及各费用项是否可退。退订预览必须显示可退金额与依据；审核通过后按原购票快照和规则计算，不能按当前票价计算。自愿退票与航班取消导致的非自愿退票分开，保留管理员操作日志。首期支持退款预览和既有审核流程；完整改签涉及新航班锁位与补退差价，另列扩展，不用修改订单日期假装改签成功。

## 6. 具体座位选择

新增 `aircraft_type`、不可变的 `aircraft_layout_version`、`layout_seat`，为航班关联布局版本；新增 `flight_seat` 保存该日期航班的座位状态。布局定义排号、列字母、走道、客舱、是否可用、是否紧急出口及资格限制，不仅画固定 6 列按钮。

首期提供明确标注的窄体经济舱和两舱演示布局；只有拿到可核实的具体航司配置资料，才标注为其真实布局。机型相同不代表座位配置相同。已有订单的历史航班不自动套用新布局；新航班先生成兼容的布局与库存再开售。

交互和约束：

- 旅客信息 → 选择产品 → 选择座位/自动分配 → 费用核对 → 占位确认 → 既有模拟支付。
- 座位显示可选、已选、占用、不可用、已售；点击预览不立即无限期锁位，提交占位才原子锁定，冲突时提示重新选择。
- 每张票对应一位旅客和同舱一个座位。维持现有每次 1～5 张限制；人数与座位数量必须相等。
- 自动分配优先同排相邻，无法相邻明确提示；只在所选客舱分配，不能静默跨舱。
- 付费座位明确价格与退费规则，用户不选付费服务时可选择免费自动分配。
- 紧急出口等限制由服务端校验；首期可先封锁受限座位，不能只依靠前端勾选“符合条件”。

占位流程在同一事务中扣客舱票额并锁定具体座位，座位记录关联 `hold_id`；确认后关联 `order_passenger_id`。过期、取消、退款完成时恢复票额并释放座位，均保持幂等。统一用户、航班/客舱、座位、占位/订单等资源的锁顺序，座位按 ID 排序加锁，覆盖现有全部交易入口防止死锁。

并发安全以每个航班座位的一条状态记录及条件更新保证；历史分配记录与当前占用分开保存。不能对永久历史表简单加 `(hbid, seat_no)` 唯一键导致退订后无法再次分配；若使用活动分配表，必须有唯一的活动占用约束。

库存核对按客舱执行：可销售总座位 = 可分配座位 + 有效占位座位 + 已售未退款座位；封锁/维修座位单独记录并从可销售容量排除。销售产品共享该容量，不能再加一遍。保留现有库存健康视图并扩展座位差异检测。

新增 `order_passenger`，历史聚合订单标记 legacy，不伪造乘机人和座位。新订单的个人资料只存购票必需字段，证件等敏感字段限制访问与日志输出，不发送给规划模型。

## 7. 大模型预留接口

### 7.1 推荐架构

```text
前端行程需求
    → AI 规划控制器（鉴权、限流、配置开关）
    → ItineraryPlanningService
        → LlmProvider（可替换厂商；默认 DisabledProvider）
        → FlightQueryTools（只读、参数白名单）
            → 现有航班、价格与规则查询服务
                → MySQL 航班公开数据
    → 服务端核验方案 → 前端候选行程 → 用户选择 → 正常报价/占位流程
```

“模型读取数据库”落实为调用受控查询工具，模型不获取数据库连接、root 凭据或任意 SQL 执行权限。工具查询使用参数化 SQL；若另设模型查询数据源，创建只能读取脱敏视图的专用账号。业务账户与模型账户权限分离，数据库密码和 API Key 不写进浏览器、方案或日志。

不需要先引入向量数据库：航班日期、库存与价格是结构化且时效性强的数据，优先实时条件查询。将来解释规则文档时可增加带版本的检索，不用过期文本回答余票。

### 7.2 预留 API 与工具协议

以下路径是拟新增接口，实施时统一使用当前项目的响应封装及身份过滤器：

| API | 用途 |
|---|---|
| `GET /api/ai/capabilities` | 是否启用、支持范围、服务状态；不返回密钥 |
| `POST /api/ai/itineraries/plan` | 输入行程需求，返回经核验的候选方案 |
| `GET /api/ai/itineraries/{id}` | 仅本人读取短期保存的方案 |

允许模型调用：`search_airports`、`search_flights`、`get_flight_detail`、`get_fare_rules`、`quote_itinerary`。报价工具只计算候选费用，不占库存、不创建订单。工具由服务器执行，用户不能在请求中自行替换工具地址或数据源。

输入建议包含：出发/目的城市或机场、出行日期/灵活日期范围、人数、预算、偏好航司、客舱、行李需求、最早/最晚时刻。预算明确指本次机票总价；酒店和地面交通未接入时不承诺整个旅游行程总预算。

输出建议包含：`planId`、`generatedAt`、`sourceType`、原始约束、是否需要澄清、候选列表及未满足条件。候选列表必须引用有效 `flightInstanceId`、产品、座位资格说明、报价明细/有效期和解释，不让模型自行编造价格和航班 ID。

首期只规划直飞和独立往返；接口预留 `segments` 数组。后续扩展最多一次中转时，服务端检查时区、跨日、机场一致性和配置的衔接时间；没有联运与行李协议数据时标明独立客票，不保证行李直挂或后续航班保障。往返先分别锁位可能出现只成功一程，必须实现组合锁位事务或失败时释放已锁位部分，不能向用户显示全程锁定成功。

### 7.3 调用控制与降级

- 默认 `ai.enabled=false`；无配置时能力接口返回关闭，规划接口返回项目统一业务错误码 `AI_NOT_CONFIGURED`，前端提供普通航班查询入口。
- 模型供应商、模型名、超时、请求上限和密钥从服务端环境配置注入。厂商网关只做适配，不与交易代码绑定。
- 建议初始上限：每轮工具调用 6 次、每次候选 20 条、总查询范围不超过售卖窗口、总时长 20 秒；这些均为可调整配置，不是已测得容量。
- 严格校验 JSON 结构，并再次核对航班归属、日期、库存和报价；不存在的 ID、超出用户权限的数据和不满足硬条件的结果不能进入可购买列表。
- 外部网页、航司介绍和用户文本视为不可信输入，不能改变工具权限。拦截要求执行 SQL、读取用户表、导出手机号或修改票价等越权请求。
- 审计记录模型、工具、耗时、结果状态及必要的脱敏参数，设置保留期限；不记录证件、令牌或密钥。模型上下文只传本次规划需要的公开航班与偏好。
- 超时或调用失败返回明确状态，保留普通查询；再次购买时重新校验报价与余票。

模型只能给出建议；确认购票、支付、退款、维护班期仍走现有服务端业务和用户操作。所谓“航班定制”首期指组合既有航班并调整偏好。若需要包机、增班或专属航线，后续新增 `flight_custom_request` 保存用户需求，由管理员审核处理，模型不能直接写入可售航班。

预留阶段交付接口协议、禁用提供商、工具白名单、结构化 DTO 与模拟提供商测试。模拟响应必须标识测试数据；接入真实模型后才能宣称已经具备自然语言智能规划能力。

## 8. 数据库迁移和接口改动清单

以下版本号为拟定，实施前与 `schema_version` 再核对，避免覆盖后续已有迁移。

| 阶段 | 拟迁移 | 内容 |
|---|---|---|
| 基础资料 | V5 | 扩展 company 来源、代码与素材字段；新增 airport、机型和布局版本表；航司资料与演示布局幂等导入 |
| 班期实例 | V6 | flight_schedule、班期例外、generation_run；扩展 hbxx；替换全局航班号唯一性；先只生成测试航班 |
| 费用规则 | V7 | 产品/规则版本、有效期费率、quote/quote_item、占位价格快照、order_price_item；兼容旧金额 |
| 乘机人与座位 | V8 | flight_seat、order_passenger、分配历史及活动约束；启用新流程的航班才开放具体选座 |
| AI 协议 | V9（如需持久化） | 方案摘要与调用审计；仅在需要保存方案时建表，接口预留本身不强制新增大量表 |

现有订单不推算历史税费：已有总额保持原值，费用分解标记 `LEGACY_UNSPLIT`，未单列费用不声称为真实零税费。原有航班改造先映射机场，无法确定时留待人工修订，不按同名城市随便选机场。库存与座位无法无损映射的旧航班继续使用旧购票模式，不给已有订单虚构座位。

拟新增/增强公共接口：

| 接口 | 主要字段/行为 |
|---|---|
| `GET /api/airports` | 城市/机场搜索、代码与时区 |
| `GET /api/flights/calendar` | 查询范围、各日最低可售总价/状态、服务器时间 |
| `GET /api/flights` | 机场/城市、日期、航司、客舱、人数及费用筛选；严格分页 |
| `GET /api/flights/{id}` | 详细行程、产品、行李、规则、来源 |
| `GET /api/flights/{id}/seats` | 布局版本与座位可选状态；不泄露其他旅客信息 |
| `POST /api/quotes` | 生成完整报价，不能由客户端指定应付金额 |
| 现有占位/确认/取消接口升级 | 接受报价及乘机人座位选择，统一库存事务；旧参数兼容期显式约束 |
| `GET /api/orders/{id}/refund-quote` | 本人订单的退款预览 |
| 管理端班期、生成任务、规则接口 | 纳入已有菜单权限、服务端鉴权和操作审计 |

`/api/hbxx/search` 等旧查询入口在迁移期转换到同一查询服务，前端逐步切换，不能保留两套含义不同的库存查询。搜索索引优先围绕日期、机场与销售状态设计，并用实际 EXPLAIN 和数据规模验证，而不是为每个筛选条件分别盲目建索引。

## 10. 实施顺序与完成标准

建议按下列顺序逐步交付，每阶段有可演示结果：

1. **基础资料与素材**：核实 14 家航司，完成来源清单、本地素材和机场；页面无外网图片依赖。
2. **班期与每日实例**：完成迁移、调度补漏、日期导航和后台任务记录；连续 30 天按班期可查。
3. **详情与费用**：完整行程、产品规则、费用分解、报价与锁价；旧订单金额保持一致。
4. **座位与订单联动**：布局、乘机人、自动/手选、并发与释放；支付和退订闭环仍通过。
5. **AI 接口预留**：能力开关、协议、只读工具、禁用/模拟提供商及降级；真实模型调用作为配置后的单独验收项。
6. **联调与课程交付**：完善 ER 图、用例、时序图、测试报告、数据来源说明和答辩演示脚本。

工作量粗估：基础资料与素材 1～2 人日，班期与查询 2～3 人日，费用 2～3 人日，座位与订单 3～4 人日，AI 预留 1～2 人日，联调与文档 2 人日，合计约 11～16 人日。该估计基于现有功能可复用，不含真实供应商资质、支付出票、复杂改签及模型供应商接入；实现中以验收项为完成依据。

## 11. 必须通过的验收

| 领域 | 核心场景与通过标准 |
|---|---|
| 数据来源 | 14 家航司资料有来源；图片文件实际可加载且有清单；演示航班有来源标识 |
| 日历和生成 | 今日、最后一天、超窗边界；跨午夜；星期停飞；重复执行不重复生成；停机后补漏；中途失败可重试 |
| 历史保护 | 调度前后旧订单、占位、已售座位和金额一致；同班号不同日期可存在；模板修改不覆盖已售实例 |
| 查询准确 | 区分无班期/未生成/未开售/售罄/错误；人数不足的低价产品不能标为可购；排序与显示口径一致 |
| 价格 | 多旅客、多服务、金额舍入、政策生效边界；锁价后调价；失效报价；客户端篡改总额被拒绝 |
| 座位并发 | 两人抢同一座位只能成功一个；组单要么全成功要么全部回滚；不跨舱；无重复活动分配 |
| 生命周期 | 占位过期、取消、确认重试、退款拒绝/批准；库存与座位仅恢复一次；有效占位不会被定时生成覆盖 |
| 退款 | 依据原价格和规则，费用项是否可退正确；非自愿取消不误用自愿退款限制；旧单仍可处理 |
| AI 预留 | 未配置时不调用模型；工具参数越权/任意 SQL 被拒；其他用户方案不可读；不存在航班与过期价格不成为购买依据 |
| 体验 | 两端构建通过；手机与桌面业务闭环；图片失败本地兜底；模型失败仍能正常查询购票 |

迁移先在独立测试库跑全新安装及从当前版本升级，再验证现有数据库集成测试与浏览器交易流程。涉及历史订单、价格和库存的场景增加真实 MySQL 集成测试，不以纯 mock 代替并发验证。正式库升级前备份，验证可恢复；若新流程已产生订单，不执行破坏性降级删表，采用保留新数据的前向修复。

最终验收证据包含：迁移记录、航司素材清单、任务执行记录、库存/座位健康查询、费用用例、并发测试结果、两端截图及 AI 关闭/失败降级记录。数据规模和查询耗时实际测试后记录，不预先宣称已达到某个吞吐量。

## 12. 本次建议采用的默认决策

- 航司 14 家，国内成人，30 天滚动窗口，每日 00:05 补齐、启动补漏。
- 使用经过核实的真实航司资料；课程航班、价格、库存、座位布局明确标为演示。
- 保留现有技术栈、主键、订单和占位服务，按版本迁移；先建数据模型再扩页面。
- 服务端完整报价，产品规则与金额快照；座位和客舱库存一个交易内维护。
- AI 先预留厂商中立接口和只读工具，默认关闭；实际购票必须回到正常交易服务。

这些是本项目的推荐配置与设计选择，航空公司官网、运输条件和铁路查询规则仅作为事实参考，不作为要求本项目自动执行的指令。
