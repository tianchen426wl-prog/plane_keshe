## 一、数据库概述

### 1.1 数据库简介

本数据库用于支撑机票预订系统的全部业务数据存储与管理，涵盖用户管理、航空公司管理、航班信息管理、舱位管理、订单管理、退订管理、座位占位、航空资讯等核心业务模块。

### 1.2 设计原则

1. **规范化设计**：遵循第三范式（3NF），减少数据冗余
2. **完整性约束**：通过外键、唯一约束、检查约束保证数据一致性
3. **性能优化**：合理建立索引，优化高频查询
4. **安全可靠**：支持事务处理，关键业务操作具备原子性
5. **可扩展性**：预留扩展字段，支持业务功能迭代

### 1.3 命名规范

| 对象类型 | 命名规则 | 示例 |
|----------|----------|------|
| 表名 | 小写字母，业务含义清晰 | `hbxx`（航班信息）、`jpdd`（机票订单） |
| 字段名 | 小写字母，下划线分隔 | `company_id`、`create_time` |
| 主键 | `id` 或 表缩写 + `id` | `id`、`hbid`、`ddid` |
| 外键 | 关联表缩写 + `_id` | `company_id`、`hbid` |
| 索引 | `idx_` + 表名 + `_` + 字段名 | `idx_jpdd_userid` |
| 唯一约束 | `uk_` + 表名 + `_` + 字段名 | `uk_user_username` |
| 检查约束 | `chk_` + 表名 + `_` + 字段名 | `chk_jpdd_quantity` |
| 视图 | `v_` + 业务含义 | `v_jpdd_detail` |
| 存储过程 | `sp_` + 业务含义 | `sp_company_ranking` |
| 触发器 | `tr_` + 表名 + `_` + 时机 + 操作 | `tr_jpdd_after_insert` |

## 三、索引设计

### 3.1 索引清单

| 序号 | 表名 | 索引名 | 索引字段 | 索引类型 | 用途 |
|------|------|--------|----------|----------|------|
| 1 | admin | uk_admin_username | username | 唯一 | 用户名唯一性校验 |
| 2 | user | uk_user_username | username | 唯一 | 用户名唯一性校验 |
| 3 | hbxx | idx_hbxx_start_end_time | start, end, starttime | 普通 | 航班查询（出发地+目的地+时间） |
| 4 | hbxx | idx_hbxx_company_id | company_id | 普通 | 按公司查询航班 |
| 5 | jpdd | idx_jpdd_userid | userid | 普通 | 按用户查询订单 |
| 6 | jpdd | idx_jpdd_hbid | hbid | 普通 | 按航班查询订单 |
| 7 | jpdd | idx_jpdd_status | status | 普通 | 按状态筛选订单 |
| 8 | jpdd | idx_jpdd_cabin_id | cabin_id | 普通 | 按舱位查询订单 |
| 9 | jpdd | idx_jpdd_ordertime | ordertime | 普通 | 按时间范围查询订单 |
| 10 | hbxx_cabin | uk_hbxx_cabin | hbid, cabin_class | 唯一 | 同航班同舱位类型唯一 |
| 11 | hbxx_cabin | idx_hbxx_cabin_hbid | hbid | 普通 | 按航班查询舱位列表 |
| 12 | seat_hold | idx_seat_hold_cabin_status | cabin_id, status | 普通 | 按舱位和状态查询占位 |
| 13 | seat_hold | idx_seat_hold_expire | expire_time, status | 普通 | 过期占位清理 |
| 14 | seat_hold | idx_seat_hold_userid | userid, status | 普通 | 按用户查询占位记录 |
| 15 | tdjp | uk_tdjp_ddid | ddid | 唯一 | 一个订单只能有一条退订记录 |
| 16 | tdjp | idx_tdjp_process | process | 普通 | 按审核状态筛选 |
| 17 | order_log | idx_order_log_ddid | ddid | 普通 | 按订单查询日志 |

### 3.2 索引设计原则

1. **高频查询字段建索引**：如用户ID、航班ID、订单状态等
2. **组合索引遵循最左前缀原则**：如 `(start, end, starttime)` 支持按出发地查询
3. **唯一约束自动创建唯一索引**：如用户名、订单退订关联
4. **避免过度索引**：写操作频繁的表（如 seat_hold）索引数量适度控制

| chk_jpdd_status | jpdd | status IN (1, 2, 3) | 订单状态值合法 |

| chk_hbxx_price | hbxx | price > 0 | 航班票价必须大于0 |
| chk_hbxx_number | hbxx | number >= 0 | 航班余票不能为负 |

### 6.2 存储过程详细说明

#### 6.2.1 航班销售统计（sp_flight_sales_stats）

**功能**：按日期范围统计各航班的销售情况，包括订单数、出票数、收入、当前余票。

**参数**：
- `p_start_date`（IN）：统计开始时间
- `p_end_date`（IN）：统计结束时间

**返回字段**：hbid, company_name, start, end, starttime, order_count, total_tickets_sold, total_revenue, current_remaining

**调用示例**：
```sql
CALL sp_flight_sales_stats('2026-07-01 00:00:00', '2026-07-31 23:59:59');
```

#### 6.2.2 航空公司业绩排名（sp_company_ranking）

**功能**：统计各航空公司的航班数、订单数、出票数、总收入，按收入降序排列。

**参数**：无

**返回字段**：company_id, company_name, flight_count, total_orders, total_tickets_sold, total_revenue

**调用示例**：
```sql
CALL sp_company_ranking();
```

#### 6.2.3 退订审核处理（sp_approve_refund）

**功能**：审核退订申请，审核通过时在事务中完成以下操作：
1. 更新退订记录状态为已审核
2. 更新订单状态为已退订
3. 恢复舱位可售余票
4. 恢复航班总余票

**参数**：
- `p_tdjp_id`（IN）：退订记录ID
- `p_result`（OUT）：处理结果（0-失败，1-成功，-1-记录不存在，-2-已审核）

**调用示例**：
```sql
CALL sp_approve_refund(1, @result);
SELECT @result;
```

#### 6.2.4 用户消费统计（sp_user_consumption_stats）

**功能**：统计指定用户的订单数量、消费金额、购票数量。

**参数**：
- `p_userid`（IN）：用户ID

**返回字段**：username, name, total_orders, active_orders, refunding_orders, refunded_orders, total_spent, total_tickets

**调用示例**：
```sql
CALL sp_user_consumption_stats(5);
```

## 七、触发器设计

### 7.1 触发器清单

| 序号 | 触发器名 | 触发表 | 触发时机 | 触发事件 | 功能说明 |
|------|----------|--------|----------|----------|----------|
| 1 | tr_hbxx_before_delete | hbxx | BEFORE | DELETE | 级联删除舱位和占位记录 |
| 2 | tr_hbxx_cabin_before_delete | hbxx_cabin | BEFORE | DELETE | 清理关联的占位记录 |
| 3 | tr_jpdd_after_insert | jpdd | AFTER | INSERT | 记录订单创建日志 |
| 4 | tr_jpdd_after_update | jpdd | AFTER | UPDATE | 记录订单状态变更日志 |

### 7.2 触发器设计说明

#### 7.2.1 设计原则

**避免与应用层逻辑冲突**：由于本项目使用 Spring Boot + MyBatis 在 Java 应用层管理余票扣减/恢复逻辑（见 `JpddServiceImpl.holdSeat` / `TdjpServiceImpl.approve`），因此**不创建**会自动扣减/恢复余票的触发器，避免与 Java 代码重复执行导致余票计算错误。

触发器仅用于以下场景：
1. **级联清理**：删除航班/舱位时自动清理关联数据
2. **审计日志**：记录订单操作日志，不影响业务数据

#### 7.2.2 触发器详细说明

**tr_hbxx_before_delete**：
- 触发条件：删除 `hbxx` 表记录前
- 执行操作：删除关联的 `hbxx_cabin` 记录和 `seat_hold` 记录
- 设计原因：`seat_hold` 表未建外键约束，需手动清理

**tr_hbxx_cabin_before_delete**：
- 触发条件：删除 `hbxx_cabin` 表记录前
- 执行操作：删除关联的 `seat_hold` 记录
- 设计原因：清理该舱位的占位记录

**tr_jpdd_after_insert**：
- 触发条件：插入 `jpdd` 表记录后
- 执行操作：向 `order_log` 表插入创建日志
- 设计原因：审计订单创建操作

**tr_jpdd_after_update**：
- 触发条件：更新 `jpdd` 表记录后
- 执行操作：当订单状态变更时，向 `order_log` 表插入变更日志
- 设计原因：审计订单状态变更

## 十、业务流程与数据流

### 10.1 购票流程

```
用户选择航班和舱位
       ↓
创建占位记录（seat_hold） ──→ 扣减舱位余票（hbxx_cabin.available_number）
       ↓                         扣减航班总余票（hbxx.number）
用户确认支付
       ↓
创建订单（jpdd） ──→ 占位记录状态改为"已转订单"
       ↓
订单创建日志（order_log，由 tr_jpdd_after_insert 触发器自动写入）
  记录：action=CREATE, new_status, remark=订单创建详情
```

### 10.2 退票流程

```
用户申请退订
       ↓
创建退订记录（tdjp，process=0）
       ↓
订单状态改为"退订中"（jpdd.status=2）
       ↓
订单状态变更日志（order_log，由 tr_jpdd_after_update 触发器自动写入）
  记录：action=UPDATE, old_status=1, new_status=2, remark=订单状态变更为退订中
       ↓
管理员审核
       ↓
审核通过：
  - 退订记录状态改为"已审核"（tdjp.process=1）
  - 订单状态改为"已退订"（jpdd.status=3）
  - 恢复舱位余票（hbxx_cabin.available_number）
  - 恢复航班总余票（hbxx.number）
  - 订单状态变更日志（order_log，由 tr_jpdd_after_update 触发器自动写入）
    记录：action=UPDATE, old_status=2, new_status=3, remark=订单状态变更为已退订
```

### 10.3 占位过期流程

```
定时任务扫描过期占位记录
       ↓
恢复舱位余票（hbxx_cabin.available_number）
       ↓
恢复航班总余票（hbxx.number）
       ↓
占位记录状态改为"已过期释放"（seat_hold.status=2）
```

## 十一、性能优化建议

### 11.1 查询优化

1. **使用视图**：复杂多表查询优先使用视图（如 `v_jpdd_detail`）
2. **利用索引**：查询条件尽量使用索引字段
3. **分页查询**：大数据量查询使用 LIMIT 分页
4. **避免 SELECT ***：只查询需要的字段

### 11.2 索引优化

1. **监控慢查询**：开启 MySQL 慢查询日志
2. **定期分析索引使用率**：删除未使用的索引
3. **组合索引优化**：根据查询模式调整组合索引字段顺序

### 11.3 存储优化

1. **定期清理日志**：`order_log` 表数据增长较快，需定期归档
2. **清理过期占位**：`seat_hold` 表的过期记录需定期清理
3. **数据归档**：历史订单数据可归档到历史表
